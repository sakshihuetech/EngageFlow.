# WABA-wise isolation

Broadcast, API Campaigns, Execution Logs, and Inbox default to the single connected WhatsApp account resolved for the workspace. Their list and detail APIs filter by both `workspaceId` and `whatsappAccountId`. A previous account is readable only with `view=history&accountId=<workspace-owned disconnected account id>`. Historical views do not offer mutation controls, and backend mutation routes independently require the current account. The account selector uses `GET /api/whatsapp/accounts/views`; no new collection or historical data migration is used.

The external API Campaign trigger checks the campaign's stored account, connection, exact phone and approved template before contact creation, execution creation or enqueueing. A LIVE slug bound to a disconnected WABA returns `API_CAMPAIGN_SENDER_DISCONNECTED`; it is not silently rebound to the new sender. Existing queued jobs also pass through the shared sender's connected-account validation before provider submission. A current campaign sender change requires explicit confirmation and is recorded in its embedded sender-change history.

Contacts and segments remain workspace-wide for CRM use. New `OPTED_IN` evidence is explicitly bound to the current WhatsApp account using the optional embedded `whatsappConsent.accountId` field. Legacy unscoped opt-in evidence remains visible but does not authorize marketing sends on another WABA. Broadcast snapshot and worker recheck, and marketing API Campaign triggers, require matching account-scoped evidence. The editor asks for explicit confirmation before assigning consent to the active account. No legacy consent is silently rewritten. Opt-out and block states remain workspace-wide safety signals.

Historical campaign, execution and Inbox records keep their original account/phone references and delivery status; webhook correlation continues to use existing sender/message identifiers. Historical views are read-only. The UI shows previous-WABA context; active account views do not mix old records. Creating a new campaign for a new WABA requires selecting that WABA's approved template. Old Broadcast duplication is not allowed as a historical mutation.

Indexes added for bounded account-scoped lists: Campaign and API Campaign by `(workspaceId, whatsappAccountId, _id)`, and Conversation by `(workspaceId, whatsappAccountId, lastMessageAt, _id)`. Index creation should be scheduled/monitored on a production-sized MongoDB dataset. No collection is added and existing records are not rewritten.

## Operations and remaining blockers

This code does not add real user authentication or RBAC. The existing workspace resolver must be replaced with an authenticated, role-aware resolver before multi-tenant production access; account ownership checks alone do not establish an authorized user. The development-only consent bypass must remain disabled in production. Existing unscoped opt-in records need fresh, auditable current-WABA confirmation before marketing sends. Run staging tests for account switching, historical pagination, stale queued jobs and webhook delivery, using mocked Meta responses; no live send is required for this change.
