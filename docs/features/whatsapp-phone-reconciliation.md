# WhatsApp phone reconciliation

Setup reads workspace-owned connection, WABA, phone and credential records; its normal page load does not contact Meta. **Refresh Meta Assets** calls `POST /api/whatsapp/setup/refresh`, which uses the stored server-side credential to read the WABA and the complete paginated `/{waba-id}/phone_numbers` list. Refresh no longer calls `subscribed_apps`. A complete, valid list is reconciled in a MongoDB transaction: returned phone records are updated, and previously stored phones absent from that WABA's list are retained with `registrationStatus: UNAVAILABLE`. An empty valid list makes all its previous phones unavailable. Incomplete pages, invalid phone status or provider errors abort without changing local assets. The UI excludes unavailable phones and reports an unsuccessful refresh as unverified for that session.

Connection and WABA statuses are stored asset states, not live probes. Webhook subscription is the last successful onboarding confirmation, not a fresh delivery check. Template Sync is independent: it reads the connected WABA's Meta templates and updates their status only after a successful provider response; phone absence does not alter template approval.

**Connect Phone Number** opens the existing Meta-hosted Embedded Signup only after a user selects Standard Cloud API or WhatsApp Business App Coexistence. The latter requests Meta's Coexistence flow through the existing app configuration; eligibility and configuration are controlled by Meta. The backend exchanges the authorization code, verifies the exact WABA and selected phone from Meta and checks workspace ownership. A verified connected/registered phone is send-ready; a Standard phone returned as `PENDING` is stored as pending for the existing explicit Register phone step, but cannot send. Coexistence requires a verified connected/registered phone. Coexistence completion without a phone ID, cancelled popup, invalid assets or unsupported status fail without changing the local connection. No WhatsApp Business App migration or deregistration is performed here. Onboarding alone does not prove webhook delivery or production send eligibility.

Broadcast and API Campaign readiness check the stored phone's availability; the shared sender repeats that gate immediately before transport submission. A phone removed at a successful refresh cannot be queued or sent through the old ID. A deletion not yet observed by refresh can still appear locally ready; controlled staging verification and periodic reconciliation are needed before claiming production readiness. Existing historical campaigns, messages, templates and phone records are retained.
